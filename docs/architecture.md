# Architecture

abap-cli follows a three-layer design with clear separation of responsibilities.

## The Three Layers

| Layer | Directory | Language | Responsibility |
|-------|-----------|----------|----------------|
| **CLI** | `src/abap_cli/` | TypeScript | Thin client: HTTP calls to SAP, file I/O, result display |
| **SAP** | `abap/` | ABAP | Bundled ICF service under `/sap/abap_cli`: DDIC + HTTP + TRAN + XSLT + SM59 + SRFC + OA2P + authorization-object CRUD, table data query, report runner, MIME repository, textpool read, version source, setup |
| **Agent** | `skills/` + `agents/` | Markdown | Skill prompts and multi-step workflow orchestration |

```mermaid
graph LR
    A[Agent / User] -->|CLI commands, --json| C[abap-cli CLI layer]
    C -->|ADT REST API| S1[SAP ADT]
    C -->|RESTful JSON| S2[SAP ICF service /sap/abap_cli<br/>DDIC · HTTP · TRAN · XSLT · SM59 · SRFC · OA2P · auth · data · run · mime · textpool · version + setup]
    C <-->|local files| F[src/ AFF flat layout]
```

### Key decisions

- **Session reuse is store-first, not write-first** — a CLI process may keep its SAP session open only when the encrypted jar landed in a *durable* store (`ABAP_CLI_SESSION_DIR` → `~/.abap-cli/sessions` → `<workspace>/.abap-cli/sessions`), contains a stateful `SAP_SESSIONID_*` cookie *and* its `sap-contextid`, and replay has not been paused after repeated auth failures. Everything else is logged out at command end. `$TMPDIR` is not a store: it cannot prove the next process can read the jar. The cookie policy matters because S/4HANA silently routes a request that carries the session cookie without its context cookie into a new SAP session (one orphan per command in SM04); see `docs/architecture.md`, `wiki/commands/session.md` and `wiki/design-decisions/015-session-lifecycle.md`.
- **ADT via `abap-adt-api`** — source objects (Class/Interface/Program/Function Group) use the standard ADT REST API: search, object structure, source GET/PUT, lock/unlock, content-based syntax check, ABAP Unit runs (`test`), activation, object creation, transport management, usage references (`where-used`).
- **Thin client** — the CLI only orchestrates HTTP calls and file/result handling; business logic stays on the SAP side.
- **Unified output** — every command uses `output/json.ts` (`printResult`/`printError`) so `--json` output is consistent across commands and parseable by agents. `OutputMode` is `'human' | 'json' | 'pretty-json'`; `--json` is compact (token-efficient), `--pretty-json` is indented. `stripEmpty()` recursively trims empty `{}` / `[]` from `data` in JSON modes.
- **Workflow orchestration** lives in `flows/edit/`: one coordinator per command plus per-type modules. `create.ts` (dispatcher) with `create-{ddic,http,tran,xslt,ttyp,msag,ddls,sm59}.ts` and the shared `ucon-object-flows.ts` (`SRFC` / `OA2P`), `create-local.ts`, `create-fugr-func.ts`; `pull.ts` with `pull-{source,ddic,http,transport,xslt,textpool,remote,package,tr,ttyp,msag,ddls,srvd,bdef,cds-extension,sm59}.ts` plus `ucon-object-flows.ts`; `push.ts` with `push-object.ts`, `push-fugr.ts`, `push-textpool.ts`, `push-{xslt,ttyp,msag,ddls,sm59}.ts` (with the shared per-type ADT content helpers `ttyp-adt.ts` / `msag-adt.ts`); `delete-sm59.ts` and `sm59-shared.ts` own the SM59 lifecycle rules (RFCDEST name validation, no package / transport); the authorization-object family has one type-agnostic flow set (`{create,pull,push,delete}-auth.ts` + `auth-shared.ts`) driven by `formats/auth/<type>.ts` specs; the authorization-object family has one type-agnostic flow set (`{create,pull,push,delete}-auth.ts` + `auth-shared.ts`) driven by `formats/auth/<type>.ts` specs; the authorization-object family has one type-agnostic flow set (`{create,pull,push,delete}-auth.ts` + `auth-shared.ts`) driven by `formats/auth/<type>.ts` specs; AFF objects use `{create,pull,push,delete}-aff.ts` + `aff-shared.ts` (ADT blueSource for the writable four, ICF `/aff` GET for the `ENHO` / `ENHS` pull); `activate.ts` (inactive-item activation); `deploy-flow.ts` (deploy + status) with `deploy.ts` (bundled-source assembly) and `deploy-merge.ts` (release-form merger); plus `run-flow.ts` (classrun / wrapper static method), `select-flow.ts` (SE16N equivalent), `tcode-flow.ts` (TSTC → TSTCT), `where-used-ops.ts`, `search-flow.ts` (ADT quickSearch paging/filters), `status.ts`, `diff.ts`, `inspect-ops.ts`, `doctor-checks.ts`, `atc.ts`, `core/check.ts` (syntax / content / ATC validation), `core/unit-test.ts` (ABAP Unit run: level validation, flags, summary + failures projection), `core/whoami.ts` (system-side connection identity via the ICF `/whoami` endpoint). Shared resolution lives in `core/`: `core/resolve.ts` (object URL + parts resolution, packageName from the search hit), `core/transport.ts` (`resolveTransport`: `--tr` > config > user's open request > error; `isLocalPackageName` / `transportForPackage` for `$`-prefixed local packages). `push.ts` resolves the transport **per object** (`transportInfo` binding first, local packages free). Commands stay thin: they parse arguments and print the `{ data, human }` result the flow returns.
- **AFF JSON artifacts share one contract** — `formats/artifact.ts` defines `JsonArtifact<TLocal>` (read / write / validate / load) and `WireArtifact<TLocal, TWire>` (+ `toWire` / `fromWire`), with optional `beforeWrite` (pre-write schema gate) and `validate` overrides.
  The eleven JSON format modules (TTYP / MSAG / DDLS / ENQU / NROB / HTTP / TRAN / XSLT / SM59 / SRFC / OA2P) declare their artifact with `defineJsonArtifact` / `defineWireArtifact` instead of repeating the same file+schema plumbing; HTTP/TRAN use `beforeWrite` to keep their validate-before-write contract (CLI envelope stripped first). SM59 / SRFC / OA2P are local-extension documents (upstream AFF has none of those formats), so their artifacts validate against the matching `*-v1.json` and strip the server-owned identity / admin fields on pull.
  DDLS keeps a bespoke asymmetric wire mapping (the source lives in the sibling `.acds`); XSLT likewise pairs with a sibling `.xslt.xml` source and normalises line endings through one `normalizeXsltSource()` implementation; DDIC is the remaining format module with custom sidecar I/O. The routing table's `aff-json` validator consumes the same artifacts.
- **AFF objects are schema-driven, not format-mapped** — `APLO` / `CHDO` / `EVTB` / `SMBC` / `ENHO` / `ENHS` vendor the official upstream AFF v1 schemas (`aplo-v1.json` … `enhs-v1.json`) exactly like the other AFF types, and are discovered / validated through the same `aff/router.ts` suffix table + `schemaPathFor()` (`abap validate:aff` covers their `<token>.<type>.json` files). Unlike the per-type format modules above, there is no local↔wire translation: the AFF JSON document *is* the object payload, so these six types need no field projection. Their channels are split by capability: `APLO` / `CHDO` / `EVTB` / `SMBC` read and write the official AFF JSON through an ADT blueSource resource (`source/main`; lock / save-activates / transport), while `ENHO` / `ENHS` are pull-only through the read-only ICF `GET /aff/<TYPE>/<NAME>` route because SAP's AFF handler for these two types has no working write or delete implementation (`flows/edit/*-aff.ts`, `formats/aff/bundle.ts`).
- **DOMA/DTEL long text is a 0..1 AFF companion, not an object type** — `formats/docu/json.ts` owns the `docu-v1.json` document (`formatVersion` + `lines[]`), the `<name>.<type>.docu.json` filename rule and the wire normalization; `flows/edit/docu-companion.ts` owns the pull/push decisions (best-effort pull, validate-before-main-write push, `lines: []` = delete). `DOCU` is a schema/companion identifier only: no `types/registry.ts` row, no `abap create` path, no `abap types` entry — it is reached solely as a companion of DOMA/DTEL. `aff/router.ts` routes the two companion suffixes to it so `abap validate:aff` validates them, and `aff/companion-check.ts` does not require them (0..1).
- **DEVC (package) is one ADT resource, not an AFF artifact** — `formats/devc/json.ts#wireToLocal` maps the `pak:package` XML (`GET /sap/bc/adt/packages/<name>`) onto `devc-v1.json`; `buildCreateWire` assembles the `POST /sap/bc/adt/packages` body. The package has no include / source / activation, so create and pull are dedicated handlers (`flows/edit/{create,pull}-devc.ts`) instead of the generic ADT source path, and delete is a lock-free `DELETE` with a one-shot fresh-session retry when a stale ADT session holds the enqueue lock (`delete-devc.ts`). ADT exposes no package update endpoint, so push is rejected via the registry's `pushUnsupportedReason` (`TYPE_NOT_SUPPORTED`).
- **Type pools are AFF metadata + classic ABAP source** — `TYPE` keeps the upstream AFF layout (`type-v1.json` header + `.type.abap` source) and writes through ADT `/ddic/typegroups` (`TYPE/DG`, five-character names). Metadata updates happen under the same lock as the source write so the AFF description survives a pull → edit → push round-trip. Table types (`TTYP`) are pure DDIC metadata and therefore carry no ABAP companion — the pseudo-DDL `.type.abap` sidecar was removed because `.type.abap` is the AFF type-pool filename.
- **CDS technical objects are ADT metadata + `.acds` source pairs** — `DTDC` / `DTEB` / `DSFD` / `DRTY` keep the CDS source in a sibling `.acds` file (same layout as DDLS) and write it through `source/main` under a lock, then activate; the AFF header description is synced through the metadata resource so a pull → edit → push round-trip keeps it. `DSFI` has no sidecar: its `source/main` *is* the AFF JSON document, so the local file and the wire body are the same shape. Endpoint/media-type/projection knowledge lives in `clients/cds-tech.ts`; the four flows live in `flows/edit/{create,pull,push,delete}-cds-tech.ts`. Two SAP-side gates are surfaced, not worked around: DTEB needs a bufferable view entity, and DSFD writes need the `DD_CDS_DSFD` user parameter (mapped to `DSFD_FEATURE_NOT_ENABLED` with SU3 instructions).
- **Application jobs are one AFF JSON document over a blueSource resource** — `SAJC` (catalog entry) and `SAJT` (template) keep the official AFF v1 document locally (`<name>.sajc.json` / `<name>.sajt.json`) and write it to the ADT `/sap/bc/adt/applicationjob/{catalogs,templates}` `source/main` under a lock, then activate. The JSON document model is release-dependent: the reference SAP_BASIS 757 serves the flat `className`/`reportName` model, while current AFF v1 uses `generalInformation`/`exitClasses`. The CLI probes the `$schema` sub-resource and translates; fields the target model cannot carry are rejected by name instead of silently dropped. The header description is synced through the metadata resource in the same lock, and referenced objects (executed class, catalog entry) are validated by SAP at save time — its generic rejection is mapped to an actionable error in `clients/appjob.ts`.
- **ATC configuration objects are ADT XML resources over AFF JSON** — `CHKC` / `CHKO` / `CHKV` are AFF-native, pure-JSON objects, but ADT exposes them as versioned XML envelopes (`chkcv1` / `chkov1` / `chkvv4`) rather than source or JSON documents. `clients/atc.ts` owns the URL / media-type / XML ↔ AFF projection; `flows/edit/{create,pull,push,delete}-atc.ts` own the lifecycle. Create and push write the resource and then activate it (the object is inactive otherwise); there is no ICF fallback because the underlying ATC persistence has no ICF channel. `abap-adt-api` has no endpoint for these types, so the requests are hand-written like `clients/srvb.ts`.
- **SM59 HTTP destinations are system-table entries, not repository objects** — `SM59` (only `RFCTYPE='G'`, HTTP connection to external server) is a client-independent `RFCDES` row: the definition is encoded in `RFCOPTIONS` and the short text lives in `RFCDOC`. There is no TADIR object and no CTS transport path, so the registry marks the type `packageNotApplicable` and `create` / `push` / `delete` reject an explicit `--package` / `--tr` instead of recording a fake transport. The local side is the local-extension `sm59-v1` document (`targetHost` / `port` / `protocol` / `pathPrefix` / `description`, description ≤ 72 chars). Create uses the maintenance-API defaults for options the v1 model does not carry; push loads and keeps the API-known attribute values but the API rebuilds `RFCOPTIONS` on save, so legacy option codes SAP shipped on old destinations are dropped — pull → push is lossless only for destinations this type created (documented as a limitation). The SAP handler uses `SRFC_DESTAPI` (`CL_DEST_FACTORY` / `CL_DEST_HTTP_EXT`) rather than writing `RFCOPTIONS` by hand and rejects non-G destinations with `SM59_TYPE_NOT_SUPPORTED`.
- **Authorization objects are local JSON documents over hand-written ICF routes** — `AUTH` / `SUSC` / `SUCU` / `SUSH` / `SUSO` have no ADT resource and no upstream AFF handler, so each type owns a spec module under `formats/auth/` (document shape, name / filename rules, wire mapping) and one route `/auth/<sub>/<name>` in the bundled service. The family flows (`flows/edit/{create,pull,push,delete}-auth.ts`) stay type-agnostic: `create` POSTs the document, `pull` GETs it and strips the read-side `name` / `package`, `push` probes then PUTs (update-only), `delete` DELETEs. The package and transport request travel as query parameters; `$`-prefixed packages are transport-free, everything else needs `--tr`. The SUSO SAP_ALL / SAP_NEW regeneration is an explicit opt-in (`--regenerate-profiles` → `regenerateProfiles=true`) and is skipped by default; SUCU authorization groups can only be deleted in local packages because the ICF session cannot record a CTS delete entry. `SUSH` reuses the upstream AFF `sush-v1` document; the other four are local schema extensions (`auth-v1` extends the upstream field format by the SU20 exit/activity fields).

  - `DEVC` is a handler route on ADT for create / pull; it intentionally has no push row, and `ObjectTypeEntry.pushUnsupportedReason` supplies the rejection text the push flow emits.

## SAP Layer (`abap/`)

The bundled ICF service under `/sap/abap_cli` is maintained in two forms generated from the same sources.

**Development tree** — `abap/src/` keeps the service as 30 normal global classes, in the same abap-file-format flat layout the CLI writes (one `<name>.clas.abap` holding definition + implementation, plus a canonical `<name>.clas.json` per class; there are no per-type or per-object directories):

- **`ZCL_ABAP_VIBE_ICF`** — HTTP handler (`IF_HTTP_EXTENSION`): a thin front controller that dispatches `/ddic/*`, `/http/*`, `/sm59/*`, `/srfc/*`, `/oa2p/*`, `/auth/*`, `/auth/*`, `/auth/*`, `/auth/*`, `/auth/*`, `/tcode/*`, `/tran/*`, `/xslt/*`, `/jobd/*`, `/textpool/*`, `/data/*`, `/run/*`, `/mime/*`, `/version-source*`, `/whoami*`, `/_class-check*` into the helper classes below. The root path returns a unified JSON envelope with service id + version; unknown paths / methods return unified error JSON.
- **`ZCL_ABAP_VIBE_ICF_TYPES`** — the shared types (~100 `ty_*` / `tt_*`) in its PUBLIC SECTION; every helper class references them as `zcl_abap_vibe_icf_types=>…`.
- **Six authorization-object helpers** — `ZCL_ABAP_VIBE_ICF_AUTH_COMMON` (shared request parsing, package/transport rule, TADIR / `RS_CORR_INSERT` recording, write envelope) plus one handler per type (`ZCL_ABAP_VIBE_ICF_{AUTH,SUSC,SUCU,SUSH,SUSO}`) serving `/auth/<sub>/<name>`.

**Manifest** — `abap/deploy.json` (next to `abap/src`, deliberately outside the AFF tree) is the single source of truth for roles: `handler`, `merged[]` (development global class → release `lcl_*` local name, in stable base order), `standalone[]`. A class in `abap/src` that the manifest does not list fails the deploy.

**Release form** — `abap deploy` (default) installs 3 global classes: the handler (main + generated definitions / implementations), `ZCL_ABAP_VIBE_ICF_SETUP` and `ZCL_ABAP_VIBE_RUNNER`. The 27 merged helpers are downgraded to `lcl_*` local classes and folded into the handler's two includes in dependency order; `zcl_*` references in the handler main are rewritten to the matching `lcl_*` names. The merge is a pure string module (`src/abap_cli/flows/edit/deploy-merge.ts`): manifest validation, class-header downgrade, word-boundary rename, stable dependency topological sort, deterministic output, and a leftover-global-name guard. The generated includes are never committed.

**Development form** — `abap deploy --dev` installs all 31 classes as global objects in dependency order (shared types first, format renderers before the DDIC helper, the handler after every helper, setup / runner last) and skips the merge. Maintainers use it to iterate on a single class on a real system, where each class can be syntax-checked, activated and run on its own. The two forms coexist on one system: the release form uses `lcl_*` locals, the development form uses `zcl_*` globals, and only the handler name is shared — whichever form was deployed last owns its three parts.

The ICF endpoint is **stateless** (`IF_HTTP_SERVER->SET_SESSION_STATEFUL( abap_false )` in the handler): every route does its work inside one request, and no SAP user session is kept between requests. Before this, each CLI command that used ICF left one session in SM04.

Local packages (`$` prefixed) are transport-free for ADT-backed writes and for the bundled ICF handler: ENQU / NROB create, XSLT create and VIEW / SHLP / TRAN delete treat `$`-prefixed packages as local. ICF deployments older than this change recognise only `$TMP` — run `abap deploy` once after upgrading. `TEST`-prefixed packages are not transport-free.

DEVC does not use the ICF service: packages are created / read / deleted through the standard ADT package resource (`POST /sap/bc/adt/packages`, `GET`/`DELETE /sap/bc/adt/packages/<name>`, preflight `POST /sap/bc/adt/packages/validation`), so `abap create/pull/delete DEVC` works without `abap deploy`.

`abap deploy` pushes the release form then triggers the setup class; `abap deploy --dev` pushes the development form and skips the merge; `abap deploy --diff` reports whether the installed form already matches (idempotency check). `abap deploy status` / `abap init` check deployment state/version. JSON generation on the SAP side is unified on `/ui2/cl_json=>serialize` — about 74 handcrafted JSON concatenations across the ICF handler / runner / setup classes were replaced. Development of this layer follows the **Dogfooding** principle — it is itself developed via the CLI's create → pull → edit → push loop, with `abap deploy --dev` providing the single-class development form on a real system.

## Agent Layer (`skills/` + `agents/`)

Markdown prompts that orchestrate the CLI for AI agents:

- `skills/` — 6 个随包 skill（`abap-cli` meta 路由 + setup / search / edit / data 四个领域 + performance 方法论）；每个 skill 自包含 `SKILL.md + references/ + scripts/ + assets/`
- `agents/` — 多步骤工作流 agent（`abap-developer.agent.md`）

Agents drive everything through CLI commands with `--json`, never through interactive prompts (see `AGENTS.md`).

## Design Principles

The project's repo-level contract lives in the root `AGENTS.md`; the durable design principles are:

1. **Agent-First** — everything callable via CLI, `--json` output, no interactive dependency
2. **Three-layer separation** — responsibilities kept clean
3. **abap-file-format** — local files follow SAP conventions
4. **Minimal viable scope first** — start with core object types
5. **SAP-side consistency** — ICF services follow SAP standards, unified JSON responses
6. **Security & credential isolation** — credentials never in version control
7. **Dogfooding** — SAP-side ICF code is developed using the CLI itself
